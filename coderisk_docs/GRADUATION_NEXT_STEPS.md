## 1. 当前基础与下一阶段目标

本项目已完成题目创建、代码上传、检测任务、结果存储、证据展示和 HTML 报告导出的系统原型；已实现 Java/Python 基础相似度、作用域标识符规范化、规则题目画像与动态阈值。2026年10月8日，本地 Python 38 项测试、后端 8 项测试和前端构建通过，GitHub Actions 三个检查任务通过。

当前实验工具链能够校验数据来源与集合隔离、运行对比和消融实验、输出失败案例和论文表格。已有 91 对样本为合成种子数据，用于验证流程，不能替代真实数据上的效果验证。Java 结构解析仍为简化实现，跨语言 IR 与轻量控制/数据摘要属于零生产权重的实验能力。

下一阶段的工作重点是明确本科毕设研究范围、完成开题材料、建立可追溯的数据集并验证方法效果。已有系统作为前期基础如实说明，不把已有实现重新包装成未来待完成任务，也不提前写出研究结论。

## 2. 建议题目与交付范围

建议题目：**基于题目感知与标识符规范化的编程作业代码相似风险检测系统设计与实现**。

题目最终以导师和学院审批为准。本科主交付限定为 Java 与 Python 的同语言代码对分析，重点包括题目画像、动态阈值、标识符规范化、多维相似度和复核证据。系统输出相似风险，不直接认定抄袭。

跨语言分析保留为探索性附录或未来工作。完整 CFG/DFG/PDG、语义等价、大模型训练、AI 生成识别、C 稳定支持和复杂权限系统不列为本次必须交付内容。

论文中的“标识符规范化”限定为当前支持的变量、参数、函数和类名映射，不扩展为任意语句重排、表达式交换或程序语义上的置换不变性。题目画像属于启发式规则估计，不能称为客观难度测量模型。

## 3. 开题拟回答的问题

| 问题 | 研究任务 | 判断依据 |
| --- | --- | --- |
| RQ1：题目感知阈值能否减少简单题自然相似误报，同时保持合理召回？ | 在相同综合相似度下比较固定阈值与题目感知阈值 | 总体 FPR、自然相似子集 FPR、Recall、F1；同时报告误报与漏报 |
| RQ2：标识符规范化能否提高对改名及格式、注释变化的鲁棒性？ | 比较原始 Token 与规范化 Token，并移除规范化指标进行消融 | 改名子集的分数变化、Recall 与失败案例 |
| RQ3：多维证据如何支持人工复核？ | 展示相似片段、标识符映射、题目画像和阈值分解，检查可追溯性 | 行号、代码片段、映射与分数一致性；未经用户研究不声称提高复核效率 |

以上属于待验证问题。开题中可写“设计并验证”“研究是否能够”，不能写成已经证明全面优于现有方法，也不直接使用“首创”或“国际领先”。

## 6. 文献与论文材料准备

文献按以下方向检索：代码克隆与相似度检测、Token/指纹与 AST 方法、标识符规范化、编程作业中自然相似、阈值与校准、JPlag 等基线、可解释证据。

可使用 GitHub 查找工具和源码，但正式论文论据优先来自原始论文、作者页面、出版方和工具官方文档。中文文献按学校图书馆可访问资源核查。GitHub 写作 skill 提供写作流程，不作为算法研究现状的学术证据。

每条文献记录作者、题名、年份、来源、DOI/链接、已阅读内容、可支持的具体主张及使用章节。检索到的题录与真正读过的文献分开标记；没有核实的条目不进入最终参考文献。

正式开题报告预计包括：选题背景与意义、国内外研究现状、研究内容与目标、研究方法及技术路线、实验与验证方案、可行性、前期工作、进度安排、参考文献。具体栏目以学校模板为准。

最终论文采用本科系统设计与实现结构，建议为：绪论；相关技术与方法；需求分析与总体设计；题目感知与标识符规范化方法；系统实现；测试与实验分析；总结与展望。现有 `PAPER_OUTLINE.md` 以期刊研究论文为导向，不能直接当作学校本科论文模板。

## 7. 数据与实验方案

### 7.1 数据任务

先形成小规模预实验，确认标签和方法能用，再扩充正式样本。现有 Research V4 门禁声明的真实来源缺口是 20 对 manual、8 对 verified ai_assisted、8 对 external。补齐这些类别是工具链覆盖目标，不代表样本量已经充分或实验已经达到学校要求。

本科主实验优先收集同语言的独立解答、天然模板相似、变量/参数/函数改名、格式与注释变化及人工改写。AI 辅助样本按研究需要加入；若继续采用原 Research V4 数据卡，其完整性要求仍需满足，不能通过修改标签掩盖缺口。

应覆盖不同题目与不同来源，避免围绕少量原始程序制造大量改写对充当独立样本。记录每题提交数、来源家族数、代码对数和各类分布。题目数量与来源独立性比单纯追求代码对数量更重要。

每对样本保存题目、语言、来源、关系标签、变换类型、授权或许可证、代码路径、哈希、审核状态与集合归属。关系标签依据已知生成过程或独立来源，不等于抄袭认定。无法确认关系的样本标记 UNCERTAIN，仅作失败分析。

验证集和测试集在分析前按题目及来源家族划分，同一题目或改写家族不得跨集合。功能核查使用人工检查、既有评测记录或单独受控环境；上传分析链路继续保持不执行用户代码。未经授权的学生作业不进入公开仓库。

### 7.2 对比与消融

| 实验 | 设置 | 目的 |
| --- | --- | --- |
| 阈值对比 | 相同综合分 + 固定阈值；相同综合分 + 生产动态阈值；可选验证集校准 offset | 分离题目感知机制与参数校准的影响 |
| 规范化对比 | 原始 Token 与规范化 Token，在相同样本上分析改名/格式子集 | 验证表层变化鲁棒性 |
| 融合与消融 | Token-only、AST-only、完整融合、去规范化/标识符映射信号 | 检查指标贡献与代价；明确移除后的权重处理 |
| 外部基线 | JPlag 与 PICAS 使用可对齐的同语言样本；排除情况单独列出 | 提供外部参照，不预设优越性 |
| 失败分析 | 自然模板误报、复杂改写漏报、解析失败和阈值附近样本 | 解释能力边界 |

正式运行前写清每种方法的评分、阈值、权重与分类决策。现有实验脚本能覆盖的直接复用，未覆盖的设置先实现并验证；不能仅根据实验名称推定脚本已支持全部设计。

阈值与参数只在验证集上选择，随后冻结并在测试集上评估。生产公式仍以 `FORMULA_SPEC.md` 为准；实验校准不能未经验证改写生产系数。若在测试结果暴露问题后继续修改方法，该结果应标为探索分析，最终结论需新的独立保留样本。

### 7.3 输出与解释

报告 Precision、Recall、F1、FPR、混淆矩阵、自然相似子集 FPR、改写子集 Recall、解析失败率和耗时。每张表注明样本数及可对齐范围，保留原始结果、配置、运行 ID、Git 提交与数据版本。

若做置信区间或重采样，以题目/来源家族为单位处理相关性，不把同一原始程序派生的代码对当成完全独立观测。统计结论根据实际数据规模决定，不在开题时承诺显著提升。

即使方法没有全面优于 JPlag，仍应如实报告误报、召回、耗时与解释性的取舍。负结果可以回答研究问题，不能靠继续查看测试集调整阈值来制造优势。

## 8. 工程任务的优先顺序

1. 修复会改变实验结论的解析、规范化、行号与指标一致性问题，并保留回归样例。
2. 核查所有结果能追溯到题目、代码对、算法/配置版本与证据。
3. 在新环境复现启动、分析、结果查看和 HTML 下载，保留实际演示记录。
4. 评估同步逐对任务在目标规模下的耗时及前端超时；出现实际问题后再做异步编排和重试保护。
5. 取得有效本地凭据后完成 MySQL profile 实库验证；此前明确 H2 验证与 MySQL 验证的区别。
6. 在主线稳定后改善证据定位和界面，不把更换编辑器或美化页面作为研究贡献。

不因追求功能数量扩展到用户管理平台、完整跨语言语义检测或大模型训练。

## 9. 主要风险与处理

| 风险 | 处理办法 |
| --- | --- |
| 学校要求尚未明确 | 相对周次暂不映射学期日期；取得模板后调整结构、字数和截止时间 |
| 真实数据不足 | 优先收集独立来源和可追溯改写；小规模结论限定范围，明确后续数据需求 |
| 动态阈值降低误报但损失召回 | 两者同时报告；验证集决定参数；分析不同题型的适用条件 |
| Java 简化解析覆盖不足 | 明确支持范围，补失败案例和降级说明，不宣称完整 AST/语义理解 |
| 工程或论文范围过大 | 保留同语言主线；跨语言、AI 改写扩展、复杂界面进入可选项 |
| 文档与代码存在宣传性差异 | 建立“主张—实现—证据”核对表，逐项修正文稿 |
| 格式错误或引用虚构 | 按学校模板校核，引用逐条查证，Word 结构检查与逐页渲染 |

- 学校规定的开题、中期、论文和答辩材料齐全。

- 论文、系统界面和报告对“相似风险”及实验功能的表述一致。
- 按学校要求记录并说明 AI 辅助，文稿中的技术事实经过本人核实。
